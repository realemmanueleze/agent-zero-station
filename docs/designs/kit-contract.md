## Problem Statement

This document is the kit contract for the T32 through T40 pause. It is not the T28 Nango connect design. T28 through T31 are outside this pause. They land or die on `dev` before T32 program code, as Dependencies records.

The studio needs one versioned station it can deploy separately for each client. Each deploy has its own data and, later, its own LangSmith organization. The shared thing is software: connectors, context, the approve-then-send gate, and a graph host that can pause and resume. A client UI talks to that station over the existing HTTP API. An update ships once in the kit. A client gets it by pinning a new image, after that deploy's evals pass.

## Decisions

- The product surface is three APIs on the current worker: graph host, context store, client park API.
- The graph host is two ledger tables, `waits` and `outbox`, plus the existing `decisions.send_id` unique constraint. It is not a new runtime.
- `draft` returns a body and writes a parked decision. It receives no provider client and no send function.
- `runId` is minted when the first inbound parks. The reply's next draft uses that same `runId`.
- Approve is the only transition that inserts an outbox row. Inside that request the order is: insert `queued` with `receipt` null, call the provider once, and only if the decision is still live write `receipt` while the row is still `queued`, then mark `sent` and create the open reply wait. Failure stores no receipt, marks `parked_failed`, sets `attempts` to 1, leaves the decision parked, creates no wait, and returns `send.provider_failed`.
- A crash after the provider accepts and before `receipt` is stored leaves `queued` with `receipt` null. The worker does not call the provider again for that `send_id`. The operator unblocks with `POST /park/:id/receipt` and the provider message id from the sent message. That route is control-token only. It writes `receipt` and does not call the provider. If no sent message exists, the operator Kills, and the next send is a new draft with a new `send_id`.
- A second Approve when the outbox is `sent` returns 200 and does not call the provider. A second Approve when it is `parked_failed` returns 409 `send.already_attempted` and does not call the provider. A second Approve that finds `queued` with no receipt returns 409 `send.in_flight` and does not call the provider.
- The boot scan is internal. It runs on worker start and on the same tick as the mail poll. It is not an HTTP route. For `queued` with no receipt it logs `send.in_flight` at warn and does not call the provider. The HTTP 409 `send.in_flight` is only a second Approve, or a receipt post that is not allowed. When the scan finds `queued` plus a receipt and a live decision, it marks `sent` and creates the open wait, with no provider call. When the decision is killed, it does not mark `sent` and does not create a wait.
- The open reply wait is created only after a successful send. Its `threadId` starts as the inbound thread id. If the provider returns a thread id, that value overwrites `threadId` before the response. The first-run fixture sets them equal.
- At most one open reply wait may exist for `(mailboxId, threadId)`. A conflicting insert is `run.wait_conflict`. The decision stays `sent`. There is no second provider call.
- An inbound reply loads that one open wait, sets it `resumed`, and parks the next draft on the same `runId`. It does not send. A `resumed` wait does not reopen. The next successful send creates a new wait row.
- Edit `{ body }` is allowed only while no outbox row exists. Edit does not insert an outbox row and does not call the provider. Edit after an outbox row exists is 409.
- Kill marks the decision killed, sets any outbox row to `killed`, marks any open wait `dead`, releases the producer lease, and does not send. That includes Kill after `sent` and Kill while `queued` or `parked_failed`. Kill never creates a wait. Before writing `receipt` or `sent`, Approve re-reads the decision. If it is killed, Approve drops the provider result: no receipt, no `sent`, no wait. A later Approve or the boot scan on that `send_id` does not call the provider. Approve returns 409 `send.killed`. A message that already left the provider is not pulled back.
- Passing a prior run's state in as a new invocation is forbidden. That would mint a second `runId`.
- A follow-up timer is the same `waits` row with `reason = timer`. When `wake_at` passes, the worker drafts again and parks. It does not send.
- Context reads and writes take a `tenantId`. A draft for tenant A cannot see tenant B. That is T35's must-not-leak rule, applied to the context store.
- `da_checkpoints` and `da_writes` stay unused until a ticket pins a library that writes them.
- Cockpit stays in this repo. It already speaks the park API. New fields are additive so a current cockpit can ignore them.
- Separate UI and server repositories wait until a second deploy has a date. The contract those repos will pin is this API.

## Graph host

```ts
type RunId = string
type WaitReason = "reply" | "timer"

type Wait = {
  runId: RunId
  tenantId: string
  mailboxId: string
  threadId: string
  reason: WaitReason
  wakeAt: string | null
  state: "open" | "dead" | "resumed"
}

type Outbox = {
  sendId: string
  runId: RunId
  decisionId: string
  state: "queued" | "sent" | "parked_failed" | "killed"
  attempts: number
  receipt: string | null
}
```

`receipt` is null in `queued` until the provider success is stored, and null in `parked_failed` and `killed`. It is set while the row is still `queued`, and only then may the row become `sent`. `sent` has a non-null `receipt`.

Lifecycle for the proving run: park mints `runId` and writes a parked decision. No wait and no outbox exist yet. Approve inserts `queued` with `receipt` null, calls the provider once, writes `receipt` only if the decision is still live, then writes `sent` plus one open reply wait, or writes `parked_failed` and no wait. A matching inbound sets that wait `resumed` and parks the next draft on the same `runId`.

The worker that already polls mail matches a new inbound to the single open `reply` wait on `(mailboxId, threadId)`. The proving path creates no timer row. A unit test may insert a `timer` wait and must show the worker drafts and does not send. A reply resume marks any open timer for that `runId` dead.

`da_checkpoints` is not this log. Replay is the outbox unique key and the park state, not a graph-library checkpoint.

## Context store

Instructions, skills, and memory records, keyed by `tenantId`. The draft step may read that tenant's context. It may not read another tenant's. Connector secrets stay in the existing encrypted connection store. They are not context documents and they are not prompt text.

No context-hub screen in this design. The store is an API the draft step calls. A screen is a later overlay.

## Client API

Keep T32's frozen names: `GET /park` returns `id`, `state`, `actions`, `body`. Edit body stays `{ body }`, and only while no outbox row exists.

Additive fields a v1 cockpit may ignore:

- `runId`
- `wait`: `{ state, reason, wakeAt }` or null
- `outbox`: `{ sendId, state, attempts }` or null

Portal DTOs stay a mapped view. They do not become a second park desk. `POST /park/:id/receipt` is worker control-token only. The cockpit has no button for it.

## Durability on this spine

| Area | This design | Upgrade, not provisioned |
| --- | --- | --- |
| Durable state | Ledger rows for the decision, the wait, and the outbox | A workflow engine or Kafka log |
| Replay | Unique `send_id`. Draft has no provider call. Approve calls the provider once per `send_id`. Resume loads the open wait and does not re-enter Approve. | A graph library whose paused node re-runs from the top |
| Faults | Provider failure stays `parked_failed` and increments `attempts`. `lease.held` stays 409. | Jittered backoff, circuit breakers, a second zone, bulkheads |
| Queue | The park queue is the human queue. The worker polls open waits. | A broker in front of the worker |
| Streaming | Run state is rows read by `GET /park`. | Token or event streams, backpressure, chunk limits |
| Cancel | Kill marks the decision killed, marks any open wait `dead`, releases the lease, and does not send. This includes Kill after `sent`. | A distributed cancel context |
| Rollback | Kill before send. After send, a new parked draft. | A saga that pretends a sent message can be undone |

A dead-letter queue is the upgrade for rows that sit in `parked_failed` past an attempt count you have not set. This design does not pick that count.

## Reviewer Concerns

Disposition: CONCERNS_RECORDED

Stop: MAX_ITERATIONS

### R3-1 — completeness

**Problem**

> After a successful provider call, a crash before the receipt is stored leaves outbox queued with no receipt; second Approve and boot then return 409 send.in_flight forever, never mark sent, and never create the open reply wait—so the proving run cannot resume even though the message was sent.

**Remedy**

> Define recovery for that window (e.g. persist a pre-call claim or write the receipt in the same step that makes the send durable) so a successful provider call can still become sent with an open wait without a second provider call, or explicitly document that this case is operator-manual only and how to unblock the run.

### R3-2 — consistency

**Problem**

> Decisions and the queued recovery rules branch on whether the outbox row has a provider receipt, but the Graph host Outbox type only lists sendId, runId, decisionId, state, and attempts—no receipt field.

**Remedy**

> Add the receipt (or equivalent claim) field to the Outbox type and state when it is written relative to queued, sent, and parked_failed.

### R3-3 — completeness

**Problem**

> Decisions require that a queued outbox row that already has a receipt move to sent and get its open wait with no provider call, but the failing eval only covers queued with no receipt (409 send.in_flight) and never asserts the receipt-claimed recovery path.

**Remedy**

> Add a failing-eval case: Approve or boot on queued with a receipt yields sent, one open reply wait, and zero additional provider calls.

### R3-4 — completeness

**Problem**

> Kill while queued is committed, but the design does not say what happens to the outbox row, whether a late provider success from an in-flight Approve may still write sent and create a wait on a killed decision, or what Approve/boot returns for that send_id afterward.

**Remedy**

> Specify Kill’s effect on a queued/in-flight outbox so a late provider success cannot revive a killed decision, and state the durable outbox outcome plus the post-Kill Approve/boot response for that send_id.

### R3-5 — clarity

**Problem**

> Decisions name a boot pass that finds queued with no receipt and returns 409 send.in_flight, but never define what a boot pass is (worker restart job vs HTTP), when it runs, or who receives that status.

**Remedy**

> Define boot pass as an internal recovery scan or an API, when it runs, and whether send.in_flight is an HTTP response, a log/metric only, or both.
